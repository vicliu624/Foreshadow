# 资源生命周期审核 — 2026-11-25

[English](2026-11-25-resource-lifetime.md) · 简体中文

## 范围与现场证据

用户报告 Debian x64 主机 `.42` 运行一夜后出现 `Too many open files`，随后重启了
电脑。原进程及其描述符表已经不可用，因此本次审核区分“已复现的实现缺陷”和“对当次
故障的归因”。

工作区修改基于 `9bfeb363b5489018e0c6e293ddc5d9e826d387da`。测试在 `.42` 现有
本地 Runner 账号的隔离源码／构建目录中执行，不替换已安装的 0.2.15，不修改其签名
目录，也不打开实体 RSPdx-R2。本报告不声称完成 Windows／macOS 完整正式归档验收或整夜硬件测试。

随后补做的 Windows 原生 MSVC 客户端预检，在恢复原始未修补依赖时复现失败，应用
审核过的补丁后通过。一次完整关闭的 WinSock 预热及真实日志接收确认之后，32 轮创建
与 16 轮恢复的最终句柄数均等于基线 150，比较没有容差。正式 Windows 测试也改为
通过既有接收机 SDK 接口目标链接，以保留导入依赖的作用域。这属于客户端源码级验证，
与完整正式归档验收分开；macOS 和整夜实体运行仍未验证。

Windows 录制预检还复现了测试夹具问题：第一次进程通知可能只有启动诊断，Windows
文本输出还使用 CRLF。修正后的测试在截止时间内等待完整 stdout 就绪行，统一行尾，
失败时保留诊断。由于 Qt 可能自行限制子进程继承，测试还直接检查 CRT 锁文件原生
句柄的继承标志。移除 `_O_NOINHERIT` 后该原生断言失败，恢复后全部 64 轮锁／录制／
回放检查通过，前后句柄均为 148。这与原始生产代码缺陷分别记录，不豁免冻结源码的
正式发布检查。

## 已确认的缺陷与修正

| 缺陷 | 原生 Linux 上的修正前证据 | 修正 |
|---|---|---|
| 远程日志恢复时覆盖仍持有资源的套接字和线程指针，没有回收旧资源 | 注入一次日志断线／恢复，描述符从 6 增至 7 | 重连前回收已结束线程、清空指针并关闭旧套接字；不为已取消订阅的处理器重连；完成标志改用原子变量 |
| 远端构造函数取得裸日志订阅后，后续创建失败 | MAKE 被拒绝后，异常展开完成时描述符从 4 增至 5 | 在整个构造函数成功前，使用局部 `unique_ptr` 持有订阅 |
| 录制目录的锁描述符可以被子进程继承 | 原生 `FD_CLOEXEC` 检查失败 | POSIX 使用 `O_CLOEXEC`，Windows CRT 使用 `_O_NOINHERIT` 打开锁文件 |

日志重连缺陷在该恢复路径反复执行时能够累积资源。构造失败保留的是共享日志订阅／引用，
不能写成“对同一服务器每失败一次，必定增加一个描述符”。锁继承缺陷会让子进程延长
占用，并不直接证明父进程的描述符持续增长。这些证据仍不能唯一认定已重启的昨夜进程
究竟在哪条路径发生了故障。

## 所有权与架构

| 变化轴 | 所有者 | 稳定消费者 | 组装／修改位置 |
|---|---|---|---|
| 录制目录互斥与锁生命周期 | 录制后端 | 监听／会话调用者不变 | `src/backend/recordings/event_store.cpp` |
| 远程接收机连接／日志生命周期 | 可选接收机客户端的固定依赖 | 接收会话、CLI、界面与通用安装器不变 | `cmake/RemoteReceiver.cmake` 与 `third_party/soapyremote-patches/` |
| 受控依赖源码准备 | 构建组装 | 既有 DTMB 补丁调用入口保留 | 共用 `cmake/PatchPinnedSource.cmake`，DTMB 保留兼容包装 |

修改没有向稳定消费者加入接收机 ID 分支。原始上游下载不变，审核过的修改应用到当前
构建目录的私有副本；每处预期上下文必须恰好匹配一次。独立上游接收机服务没有被修改，
也不随客户端分发。

[客户端补丁说明](../../third_party/soapyremote-patches/README.zh-CN.md) 记录了保留的
原始 BSL-1.0 声明，以及采用相同许可的本地修改。Windows、Debian x64 和 ARM64 三份
审核材料配置都加入补丁清单、构建辅助文件及双语说明；仓库文件哈希和双语源码／替换
说明同步更新。

## 验收与限制

测试曾在隔离副本中移除这三处所有权修正：两个新增测试均失败，包括上面的 4→5 与
6→7 描述符变化；恢复修正后通过。

| 检查 | 同一进程中的覆盖 | 修正后的原生描述符结果 |
|---|---|---|
| `event_store_resource_lifetime` | 64 轮目录打开、冲突打开与释放；子进程保持运行时，父进程释放并重新取得锁；CU8／CI16 录制结束及回放成功、消费者异常、取消 | 基线和最终均为 5 |
| `remote_resource_lifetime` | 32 轮 MAKE 拒绝与成功创建／释放交替；通过 TCP 中继注入 16 次日志通道断线；最终取消订阅 | 基线和最终均为 4，重连期间没有逐次增长 |
| `sdrplay_backend_contract` | 额外执行 32 轮完整提供者采集，覆盖成功、取消、消费者异常、激活失败 | 基线和最终均为 4 |

这些检查使用真实的独立上游服务和独立测试接收机，并读取原生资源数量。每次操作都新开
CLI 进程会让进程退出掩盖资源残留，因此上述检查明确复用客户端进程。TCP 中继只切断
日志通道，保留控制连接。

对 `.42` 上已安装的 0.2.15 GUI 另做了隔离设置、离屏空闲观察：每秒采样一次，共 120
次，包含启动阶段，描述符始终为 11。这不覆盖原有图形桌面、持续实体采集、长时间媒体
播放或整夜重连条件。

同时审核了常规元数据／回放文件流、录制结束、接收机设备与流的作用域清理、子进程
退出及分发网络／存储的所有权；不能据此保证所有第三方路径都没有泄漏。

原生 CTest 完整注册 132 项：130 项通过，2 项因隔离 Runner 账号没有音频输出设备而
跳过，0 项失败。跳过项为 `research_audio_output` 和 `fm_playback_recovery`。
其中包含 140 秒 WSPR、60 秒 ADS-B 持续输入检查。最后一次源码／材料同步后，三项
生命周期／后端检查、扩展架构契约和许可契约再次通过。许可契约还在 Windows 上通过
全部 27 项 Python 检查，双语文档校验通过 93 对；这不构成 Windows 原生应用验收。

实际安装目录放在含中文和非 BMP emoji 的路径下，通过既有安装接收机及桌面检查，
包括模块发现、CLI 录制／回放，以及桌面回放、分析和源数据保护。首次安装使用开发
SDK 覆盖时，私有缓存中缺少原始 FFmpeg 下载归档；随后校验并补入原始归档，SHA-256
为 `e3976ef0636e9c12d68c193abc4898ab50f05be3a4996026abc60c18be7447d4`，
完整检查通过，没有跳过源码／许可声明检查。这是安装目录验收，不是新正式版本归档的发布。
