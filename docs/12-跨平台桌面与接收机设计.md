# 跨平台桌面与接收机设计

[English](12-cross-platform-desktop-design.md) · 简体中文

2026-11-05。面向全球用户，英文和简体中文均为桌面版首发要求。Windows、Debian 等 Linux 和 macOS 均为目标平台。uConsole 是低资源实机验收平台之一。支持现有 AIO2 RTL-SDR，并计划加入 SDRplay RSPdx-R2。UI 框架可替换，信号处理、录制及事件格式应独立于界面。

调制识别已有独立的实时和重放回归。桌面版现已接入中英文本地化，继续以现有 Qt Widgets 作为跨平台基线。框架对照与接收机后端仍按下文的性能和实机要求单独验收。

## 开发与验证节奏

- 按可独立验收的功能批次组织工作。先集中完成同一批的实现、译文和测试改动，再统一审查差异。纯文档修改做文档检查，沿用已有构建产物。
- 每批完成后，在主开发机复用现有构建目录，增量编译受影响的目标并集中运行相关回归。只有编译或测试失败、需要最小复现，或改动触及公共接口、依赖和构建规则时，才增加中间验证。
- 在合并或交付候选版本时运行完整平台矩阵。仅在需要验证或交付安装包时重新打包，从解包后的目录运行验收。记录提交号、已验收的平台和待验收项，确保测试结果对应实际交付的产物。
- uConsole 只保留当前已部署版本。将发布包暂存到用户安装目录，验证界面入口、设备查询和运行依赖后切换快捷方式及命令行链接，随即清理上一版、暂存包和临时构建目录。录制、用户设置与系统驱动独立存放。长期保存的源码、构建缓存和历史发布包放在开发机或 CI。

## 构建与语言

桌面构建需要 Qt Widgets 和 LinguistTools。Windows 与 Linux 最低使用 Qt 6.2，macOS 应用包最低使用 Qt 6.8。发布或 CI 使用以下命令，缺少桌面依赖会在配置阶段报错。发布包中的 Pager 工具还需要 Qt SerialPort，Debian 和 Ubuntu 使用 `qt6-serialport-dev`。仅构建命令行时可指定 `-DSIGNALSCOPE_GUI=OFF`。

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DSIGNALSCOPE_REQUIRE_GUI=ON
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
cmake --install build --config Release --component SignalScope --prefix "$PWD/stage"
```

Windows 可通过 `CMAKE_PREFIX_PATH` 指向与编译器匹配的 Qt SDK。Debian 和 Ubuntu 使用 `qt6-base-dev`、`qt6-tools-dev` 与 `qt6-l10n-tools`。macOS 可使用 Qt SDK 或 Homebrew 的 Qt。中文研究图依赖系统 CJK 字体，例如 Debian 的 `fonts-noto-cjk`。桌面研究、监听和回放使用 C++ 实现。默认构建与回归不查找 Python。仅构建程序可使用 `-DBUILD_TESTING=OFF`。需要验证遗留的 Sub-GHz 工具时，可在装有 Python 和 NumPy 的环境下显式开启 `-DSIGNALSCOPE_LEGACY_TESTS=ON`，然后运行 `ctest -L subghz`。CI 在 Ubuntu x64 的原生验收之后单独运行这组遗留测试。

启用 `-DSIGNALSCOPE_REQUIRE_AUDIO=ON` 可确保构建包含 FM 播放，配置时缺少 Qt Multimedia 会报错。Debian 和 Ubuntu 使用 `qt6-multimedia-dev`，Windows Qt SDK 使用 `qtmultimedia` 组件。桌面 CI 启用这项检查。Debian 13 容器在 x86-64 和 ARM64 任务中执行纯原生回归，并检查安装后的桌面、命令行和独立研究插件。Windows 安装后验收使用系统窗口插件和安装目录中的 Qt 库。

Windows CI 使用 vcpkg 的 `rtlsdr:x64-windows-static-md`，以静态方式链接接收机依赖并继续使用动态 MSVC 运行库。配置时选择该 triplet 及其 vcpkg toolchain，并用 `-DSIGNALSCOPE_REQUIRE_RTLSDR=ON` 要求启用适配器。归档验收调用 `signalscope devices --receiver rtlsdr`，确认解压后的 CLI 能载入后端。没有连接实体接收机时，返回的设备列表可以为空。

同一 Windows 构建通过 `SoapySDR_DIR` 选择 vcpkg 的 `soapysdr:x64-windows` 动态库，并设置 `-DSIGNALSCOPE_REQUIRE_SDRPLAY=ON`。应用包携带 SoapySDR 运行库。解压后由模拟驱动验证设备枚举、参数查询、CS16 采集和溢出处理。实体 SDRplay 仍需在目标机安装匹配的厂商 API 与 SoapySDRPlay3 模块。模块装在其他目录时，可在启动桌面或 CLI 前用 `SOAPY_SDR_PLUGIN_PATH` 指向该目录。

Windows x64 可将独立的 SoapySDRPlay3 0.5.2 模块包解压到 AMC 目录。模块放在 `lib/SoapySDR/modules0.8/`，使用包内的 SoapySDR 0.8 ABI。模块包包含上游许可证和设备编号格式修正补丁，构建来源为上游提交 `48bd8b41072534018de1d74deb3dea5874d9e0e0`。安装厂商 Hardware API 3.15 后，AMC 会按厂商注册表中的 `Install_Dir` 自动加载匹配架构的 API DLL。便携或开发环境可用 `AMC_SDRPLAY_API_DIR` 指定 API 根目录，即包含 `x64` 等架构子目录的绝对路径。 [厂商 API 安装位置说明](https://www.sdrplay.com/docs/SDRplay_API_Specification_v3.15.pdf) · [SoapySDRPlay3 上游](https://github.com/pothosware/SoapySDRPlay3)

CI 验收通过后，Windows 上传包含程序及插件的 ZIP，Debian 13 分架构上传 TAR.GZ，保留 Linux 可执行权限。Debian 归档使用目标系统的软件包提供 Qt 和 DSP 运行库。macOS 应用包与独立插件分别归档。三种验收均从含空格的解压路径启动程序，验证回放和功率报告插件。桌面验收还通过接收机设置使用的路径查找规则启动配套 CLI，确认运行的正是解压目录内的可执行文件。

录制打开、录制导出和图表保存使用 Qt 文件对话框，控件语言跟随 AMC 的语言设置。构建会嵌入 Qt 的简体中文控件词库 `qtbase_zh_CN.qm`。启用 `-DSIGNALSCOPE_REQUIRE_GUI=ON` 时，缺少词库会在配置阶段报错。Debian 和 Ubuntu 通过 `qt6-translations-l10n` 提供该词库。普通开发构建仍可从运行时 Qt 安装目录读取词库。

**语言**菜单可选择英文、简体中文或跟随系统语言。设置在下次启动时生效。跟随系统时按系统首选语言列表寻找支持项，找不到时使用英文。命令行参数 `--language system`、`--language en` 或 `--language zh-CN` 可覆盖本次启动，覆盖本身不会写入偏好。

监听窗口的调谐范围、实时电平、增益和录制列表，以及事件表和证据详情中的测量值，按系统区域格式显示小数。接收机读取统计也按该格式分组显示整数。界面语言可以独立选择。样本索引保持原样，证据详情附带的原始 JSON 可直接复制给其他分析工具。

研究面板的 FM 中心频率和以秒计的区间输入接受本地十进制数字及小数分隔符，也可输入 ASCII 数字和小数点。由事件带入的 FM 频率和音频时长摘要按区域格式显示。

录制列表中悬停在录制名称上，可查看按系统时区和区域格式显示的时间，以及原始时间戳。AMC 录制中由主机记录的时间标为主机观察时间，其他带有效时区的采集时间标为采集元数据时间。自动事件只有文件保存时间时，提示会标为文件保存时间。

监听状态的进程 CPU、当前常驻内存和峰值常驻内存通过系统接口读取，平台实现与采样处理分离。内存字段统一为字节，CPU 百分比按逻辑处理器数量归一化。报告的峰值至少包含本次会话已观测的最大当前值，避免系统接口的计数差异使峰值低于当前值。无法取得的指标省略。

macOS 应用包向系统声明英文和简体中文，默认语言为英文。界面译文由 Qt 资源提供。发布流程在解包后校验应用的语言声明，再运行桌面回放验收。源码构建使用 Xcode 26 或更新版本，以使用标准库中的 `std::jthread` 和 `std::stop_token`。

Apple Silicon 的 CI 发布包以 macOS 15.0 为最低部署目标，并写入应用包的系统版本声明。归档验收会核对声明，并检查应用、配套工具、框架及插件的 Mach-O 最低系统版本是否超出该目标。

Linux 暂存安装和 macOS 解包验收均会执行随包附带的接收机查询程序。测试环境中，RTL-SDR 应返回设备列表，已编译的 SDRplay 后端应返回缺少厂商模块的明确状态。实体接收机的采集另行验收。

桌面回放验收通过实际事件表列名验证英文和简体中文，同时检查截图能否读取。

桌面可用 `--settings-dir <目录>` 选择独立的 INI 配置目录，保存语言、接收机和检测器等偏好。该配置目录可随验收包携带，录制目录和外部插件目录仍分别由 `--output` 和 `--research-plugin-dir` 选择。桌面自动化使用临时配置目录，避免受本机偏好影响。

Windows 使用 Qt 6.3 或以上构建时，暂存安装会收集 Qt DLL、平台插件和运行时翻译。安装前缀请使用绝对路径。

原生回归包含命令行录制与逐字节重放、SDRplay 替身驱动、LoRa 前导码结构和录制保护、混合调制监听、翻译契约及桌面验收。LoRa 测试对射频夹具校验 SHA-256，并用独立的连续时间公式与固定噪声生成合成波形。混合调制测试对照同一 I/Q 流上的 LoRa、FSK、OOK、ASK 和广播 FM，覆盖 CU8 与 CI16、窄带分析开关，以及广播 FM 引起的误判。进程回归使用 Qt Core 的跨平台进程接口，翻译契约使用 Qt Core 的 XML 解析。无 Qt Core 的纯命令行构建仍可运行核心 C++ 测试，上述进程与翻译回归需要 Qt Core 才注册。该依赖只用于测试。

macOS 暂存安装生成 `stage/AMS.app`。应用包包含桌面程序、设备查询使用的命令行程序和编译进程序的翻译资源。Qt 部署脚本收集 Qt 框架和插件。Apple Silicon CI 先归档 ZIP，再解压到另一个含空格的路径。解压后逐一检查桌面程序、命令行工具、动态库和插件中的 Mach-O 加载路径，拒绝指向 Homebrew 或构建目录等外部位置的路径。随后清除 Qt 插件和动态库搜索路径的环境覆盖，从解压后的应用包运行 C++ 桌面验收。回放必须处理完原始样本，中文研究图必须实际加载到桌面。该验收也包含在纯原生测试配置中。可选接收机运行时与发行签名仍需按目标系统分别验证。

Apple Silicon 的 macOS 15 验收已通过 20 项原生测试和解包后的双语回放。打包流程在 Qt 部署后移除 Mach-O 中非系统的绝对运行时搜索路径，并重新进行临时签名和完整性校验。PDF、SVG 图标和虚拟键盘插件在缺少各自框架时从包中移除。解包检查还会核对所有 Mach-O 的 `@rpath` 依赖文件。 [验收日志](https://github.com/vicliu624/AMC/actions/runs/42291718285/job/128146544959)

桌面首次启动时按系统界面语言的优先顺序选择英语或简体中文。系统列表没有支持的语言时使用英语。可在 **Language / 语言** 菜单保存语言偏好，重启后生效。`--language system`、`--language en` 和 `--language zh-CN` 可覆盖单次启动的语言。主窗口与分析面板的英文源文本和中文译文通过 Qt Linguist 管理，中文翻译随程序嵌入。研究图继承桌面语言。SigMF 和状态 JSON 中的算法、状态标识与字段保持兼容。

接收机、SigMF 与存储的常见失败由核心层提供错误类别。桌面层按类别选择译文，状态文字的悬停提示保留原始诊断。新增接收机后端可复用现有类别，错误翻译不会进入采样回调或信号处理逻辑。

核心、命令行与外部分析工具使用英文诊断。桌面和研究图的中文文案集中在 Qt Linguist 资源。本地化契约测试检查 C++ 字符串、Qt 翻译覆盖与占位符。

自动构建矩阵覆盖 Windows x64、Ubuntu Linux x64／ARM64 和 macOS Apple Silicon。桌面离屏回归测试使用包含中文、重音字符和空格的路径，覆盖两种语言、录制重放和原始数据保护。CI 暂存安装产物供构建检查。独立发布包和实体接收机需要另行验证。

本地已验证 Windows x64 原生 Qt 和 Ubuntu 24.04 x64／WSL。独立 Debian 13 x86-64 用户空间使用 GCC 14.2 与 Qt 6.8.2 完成源码构建，17 项纯原生测试和安装后双语回放、研究绘图均通过。uConsole 的 Debian 13 ARM64 曾完成原生桌面构建，双语重放、Unicode 路径、事件存储和核心契约测试通过。新旧程序在同一段 120,000 对 I/Q 的 LoRa 录制上输出完全一致的确认事件。该结果验证重放，实时采集性能需另做对照。

uConsole 上用 `replay-events --threshold-db 11` 对照了本机原生构建（VOLK 2.5）和 CI 下载包（VOLK 3.2）。两者交替运行，各 12 次，每次处理同一段 120,000 对 I/Q 的高频边缘 LoRa 录制。两版均确认同一事件（500 kHz、SF7、SFD 样本 40250–41258），各自的重复输出逐字节一致。两版之间中心频率相差约 0.000016 Hz，电平及峰比的最大差异约 0.0000019 dB。含进程启动的中位耗时分别为 134.2 ms 和 133.3 ms。这组数据用于比较固定录制的结果和耗时，连续采集吞吐与弱信号边界需另行验证。

同机用 `detect --threshold-db 11` 复核了六份 LoRa 边界回归输入。两版均确认三份阳性输入，包括标称带内信噪比 −7 dB 的合成弱同步样本、弱 SFD 样本和搜索窗低频边缘样本。两版的扩频因子、带宽、检测时间和 SFD 样本位置一致。错误 SFD 用例开启密集短符号搜索，两版均进入方向验证且没有确认 LoRa。两份周期 FSK 误报夹具也均没有确认 LoRa。

同机还用 AIO2 在 478.5 MHz、1.75 MS/s、1 MHz 搜索宽度下分别运行两版 CLI 各 25 秒。LoRa、FSK、OOK、ASK 和 FM 检测均开启。两版各接收、分析并向事件录制管线交付 43,750,000 对 I/Q，软件队列丢弃、分析缺口和窄带跳过均为零。原生版和 CI 包的进程 CPU 占比分别约为 47.0% 和 46.0%，峰值 RSS 分别约为 70.9 MiB 和 71.0 MiB。两次为先后环境监听，均未触发录制。RTL-SDR 数据没有硬件序列号，这组计数的连续性结论仅覆盖软件管线。

可在安装了 GNU AArch64 交叉编译器、目标运行库和 `qemu-aarch64` 的 Linux 主机上复核 ARM64 核心。工具链默认在 `/usr/aarch64-linux-gnu` 查找目标运行库，可通过 `AMC_AARCH64_ROOT` 指定其他位置。以下配置用 KissFFT，并关闭桌面及实体接收机依赖。

```sh
cmake -S . -B build-arm64 \
  -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/linux-aarch64.cmake \
  -DCMAKE_BUILD_TYPE=Release -DSIGNALSCOPE_GUI=OFF \
  -DSIGNALSCOPE_LEGACY_TESTS=OFF -DCMAKE_DISABLE_FIND_PACKAGE_Qt6=ON \
  -DSIGNALSCOPE_RTLSDR=OFF -DSIGNALSCOPE_SDRPLAY=OFF
cmake --build build-arm64 --parallel
ctest --test-dir build-arm64 --output-on-failure
```

该配置已使用 GNU 13.3 交叉编译并在 QEMU 8.2 下执行，八项核心测试通过。AArch64 命令行还对实际 100.8 MHz 录制完成七百万对 I/Q 的回放识别，独立功率报告插件成功生成中文结果。

另在 QEMU 用户态模拟的 Debian 13 ARM64 用户空间中，用 GCC 14 和系统 Qt 6.8.2 构建了 AArch64 桌面程序。暂存安装后的中英文回放、研究和独立插件验证通过。实时速度 FSK 用例在模拟环境中只处理了 53 块中的 3 块窄带输入，主分析未丢样。原生 ARM64 CI 和 uConsole 实时验收仍需分别验证吞吐。

监控命令回放录制时可设置 `--replay-speed 0.05..1`，默认原速。事件仍按源录制的采样率和样本索引计算，报告会注明回放倍率。Debian 13 ARM64 的 QEMU 模拟环境已用 `AMC_TEST_MONITOR_REPLAY_SPEED=0.1 ctest --test-dir <构建目录> -R '^live_fsk_pipeline$' --output-on-failure` 通过窄带识别回归。原生 CI 保持原速，慢速结果不用于评估实时吞吐。

## 当前成本

在 uConsole 的正式 Wayland 会话中，对同一接收进程采样 15.01 秒。中心 478.5 MHz、1.75 MS/s、4 个检测线程，检测计数增加 26542080 对，软件分析丢样计数保持为零。整个进程平均使用 2.17 个 CPU 核的时间，界面主线程使用 0.224 个核，约占进程 CPU 时间的 10.3%。整个进程 RSS 约 128.7 MiB，PSS 约 107.3 MiB。测量期间另有受限的低优先级 ARM 编译。

主线程值包含事件处理及绘图等工作，未包含所有显示相关开销。RSS 和 PSS 包含 DSP、I/Q 环形预录及共享库。以上数据只描述一次现场观测，不能当作 Qt 单独成本，也不能和不同采集时段的 CLI 测试直接相减。原始结果在 `build/rf-tests/gui-live-cost-20261105.json`。

当前 SpectrumFrame 已提供频谱和 I/Q 预览，UI 每秒约接收四个频谱快照。正式基准应把同一快照序列供给各候选前端，同时对比无界面和显示时的 DSP 预算。可比较的操作包括静置、滚动瀑布、缩放、批量事件更新与切换视图。

## 模块职责与演进约束

- 接收机模块负责发现、能力和采样适配。RTL-SDR、SDRplay 和替身接收机通过相同采样接口进入监听模块。新增后端时，驱动行为应封装在适配器中，设备选择最终应消费能力与稳定设备身份。
- 监听与回放应逐步收敛到一个会话模块，由它管理输入、暂停、取消、进度与写盘策略。现有桌面回放独立实现节奏和分析路径，合并前先用同一 I/Q 录制固定两条路径的行为与差异。
- 检测调度模块应拥有队列上限、让行、线程退出和结果归并。当前窄带检测与扩展检测借用同一条提交路径。监听线程已有统一的退出所有者，部分线程启动失败时会按分析、录制、窄带检测的顺序关闭队列并等待线程退出。优先级、缺口处理和部分启动失败仍需分别做可重复的故障注入。
- 桌面主窗口消费显示快照并负责用户操作。扩展分析模块现在独立拥有 I/Q 快照、跨线程提交、分析进程、超时和结果缓存。窗口只负责开始会话、轮询和显示。状态 JSON 仍是对外协议，后续把界面消费的状态集中映射成类型化快照，避免各页面重复解释字段。

每次重构以现有入口验证。收样计数、原始 I/Q 字节、已确认事件和有界资源策略是验收依据。实时性能另用同机、同输入和同参数对照。

## 前后端与插件模型

后端拥有接收机、采样会话、信道化、检测调度、录制和回放。前端消费只读状态和显示快照，经会话命令请求启动、停止、订阅信道和打开录制。设备和任务状态以有版本的数据契约公开，Qt Widgets 是桌面适配器。显示插件只接收预览，不能阻塞采样或改变监听窗口。第一阶段维持同进程调用，等跨进程有实际需求时再选传输协议。

录制回放由 C++ 核心的 `replaySession` 执行。它从录制读取采样参数，处理播放节奏、暂停、停止和检测，并向调用方发布状态与频谱快照。桌面通过回调订阅结果，停止时会保留实际已处理的样本数。无界面环境可运行 `signalscope replay-events --input capture.sigmf-meta`，默认全速处理，不写录制，返回包含处理样本数和最近检测事件的 JSON。LoRa、FSK、OOK、ASK 和广播 FM 可分别关闭。需要按实时时间推进时使用 `--speed 1`。片段调制的批量研究入口仍是 `scan`。

片段检测的采样收集和后台调度也位于 C++ 核心。采集线程提交带绝对样本索引的 I/Q，收集器保留有界的前触发样本和约四分之一秒的分析片段。遇到样本间断会清除尚未完成的片段。分析忙碌时可以跳过新片段，桌面只负责提交采样流并轮询结果。

| 插件类别 | 输入 | 输出和职责 |
| --- | --- | --- |
| 检测 | 宽带或信道 I/Q | 调制候选、置信证据、信号位置和适用解调器 |
| 信道与解调 | 连续 I/Q、中心、带宽和采样时钟 | 音频样本、符号、比特或协议帧，保留缺口和来源 |
| 解码与解析 | 比特、帧、音频或像素流 | 有类型的音频、图片、视频、文字或结构化字段 |
| 显示与输出 | 显示快照或有类型的产物 | 瀑布图、波形、音频播放、图像、视频和文本视图 |
| 数学与工程 | 数值序列、矩阵、信号流及参数 | 变换、滤波、估计、统计、控制和模型计算 |

检测结果引用来源、样本区间、中心、带宽和证据。单击事件表中的一行可查看本地化的测量摘要及原始 JSON。事件表与摘要共用格式化逻辑，原始字段和绝对样本索引可用于复核。

回放期间或回放结束后，右键单击事件可在 **I/Q 概览**中打开原录制的对应区间。也可在事件表中选中一行，再按 **Shift+F10** 或键盘的菜单键打开相同菜单。已确认的 LoRa 事件另可用 **LoRa 结构**复核。区间依据事件的起始和结束证据生成，前后各预留约 20 毫秒，裁剪到录制边界，最多 200 万对样本。打开其他录制后，旧事件的选区入口不会关联到新文件。

桌面回放复用实时路径的 2-FSK／GFSK、OOK、ASK 和广播 FM 检测器，使用 **检测** 菜单中的选择。两条路径共用事件合并规则，确认立体声导频后会撤下同一时段内与该电台重叠的 FSK 候选。确认的广播 FM 事件可通过右键菜单 **解调录制中的 FM 事件** 打开研究工作区，自动填入检测到的频道中心，并从事件附近选取最多约五秒的预览，可再手动调整。

命令行 `monitor` 和 `replay-events` 均可通过 `--lora`、`--fsk`、`--ook`、`--ask`、`--fm` 选择检测器，取值为 0 或 1。用 `monitor` 仅监听广播 FM 时可加 `--lora 0 --fm 1`。为兼容旧命令，`monitor --fsk 1` 仍会默认启用其余窄带检测器，显式指定的选项优先。

桌面在中心频率旁提供 **搜索宽度**，以 kHz 输入，默认 1000 kHz。例如中心 478.5 MHz、宽度 600 kHz 对应 478.2–478.8 MHz。状态栏、频谱和瀑布使用会话的同一宽度。程序启动前检查搜索宽度与录制或接收机采样率是否兼容，启用 LoRa 时为候选信号带宽预留边缘。实时 SDRplay 会话还根据驱动回读的中频滤波带宽核对所需通带。改变搜索宽度只调整软件检测范围，接收机中频滤波带宽和采样率由接收机配置决定。

SDRplay 开始送样后，状态行同时显示采样跨度、软件搜索范围和驱动回读的中频滤波带宽。只有提供带宽回读的接收机才显示中频滤波值。

在实时监听的事件表中，右键单击已确认的广播 FM 行，选择 **播放 FM 音频**。从 **插件 → 停止 FM 音频** 可单独停止播放。切换电台会清除旧音频，停止监听也会停止播放。

解调器订阅当前接收机的 I/Q 并在独立线程内提取所选信道。音频队列最多保存四个输入块和 250 毫秒待播 PCM，输入积压时丢弃音频订阅块，遇到样本断点时重置解调状态。播放期间，接收机中心频率、采样率及检测任务照常运行。实时输出是 48 kHz 单声道 PCM，使用 50 微秒去加重，桌面播放需要 Qt Multimedia 和系统音频设备。

录制研究可用原生 FM 解调模块按样本区间读取 SigMF。信道中心须落在采样窗口内并留足滤波余量。输出为 48 kHz、16 位单声道 PCM WAV，滤波器启动会消耗开头少量样本。默认去加重为 50 微秒，归一化频偏为 75 kHz，可用参数选择其他配置。 [ITU-R BS.450 广播 FM 规范](https://www.itu.int/rec/R-REC-BS.450-4-201910-I)

桌面可从研究插件菜单打开 **录制 FM 音频**，选择录制和样本区间，输入频道中心频率后点击 **解调**。频率留空时使用录制中心，区间留空时分析前 30 秒以内的样本。去加重可选关闭、50 或 75 微秒，归一化频偏可选 50 或 75 kHz，默认组合为 50 微秒和 75 kHz。每次最多解调 30 秒。结果显示实际使用的参数，并可播放或导出。

```sh
signalscope fm-audio --input capture.sigmf-meta --frequency 100800000 --output fm-listening
```

调制专项插件可分别提供检测、参数估计、解调和研究视图，声明其所需的 I/Q、证据或已解调数据。一个调制可以有多个实现，通用工具也可以接受未知调制。LoRa 的典型视图是去扫频 FFT、前导码周期和 SFD。FSK 需要鉴频轨迹、频率状态和符号定时。PSK 需要同步前后的星座、相位误差和 EVM。OFDM 需要循环前缀相关、符号定时和子载波测量。FM 需要频偏分布、复合基带和导频分析，并可交给音频输出适配器。每项测量需明确估计假设、单位、适用区间和失败条件。

工程计算按图模型规划。节点声明稳定标识、版本、输入输出类型、单位、数据形状、参数和资源预算。连线前检查采样率、时钟域、单位和数据形状。不同速率通过显式重采样节点连接，反馈必须有明确延迟或求解语义。离线批处理和实时有界流采用不同调度策略。可复现结果保留源录制、节点版本、参数、区间、随机种子及处理历史。滤波、FFT、相关和估计应由共享的 C++ 数学模块提供，桌面节点和批处理入口复用。连续系统求解、控制模型与多学科节点是后续独立验收的能力。

瀑布图和 I/Q 视图已作为显示适配器装载。通用 I/Q 概览是原生 C++ 研究插件，可显示 I/Q、峰值包络、瞬时频偏、原始 I/Q 平面、时频图和平均功率谱。可按绝对样本索引选区，每次最多分析 200 万对样本。默认从录制开头读取。图题注明原录制样本区间，时轴以选区起点为零。显示抽点后的波形和 I/Q 平面只用于概览。

外部研究插件第一版使用独立的原生可执行文件。把 JSON 清单和相应平台的可执行文件放在应用数据目录的 `research-plugins` 子目录中，或启动桌面程序时用 `--research-plugin-dir` 指定目录。应用启动时扫描清单。选择工具并打开录制时才会运行该工具。在 **插件 → 管理插件… → 研究插件** 可以逐项停用外部工具。设置在下次启动时恢复，停用当前正在运行的工具会请求取消分析。

也可在同一页点击 **安装研究插件…**，选择与可执行文件同目录的 JSON 清单。AMC 把清单和可执行文件复制到 `research-plugins/installed/<插件 ID>/`，重启后加载。安装拒绝重复 ID，单个可执行文件上限为 64 MiB。由 AMC 安装的插件可在同一页卸载。卸载会把插件包移到 `research-plugins/removed/` 中的独立目录并禁用当前入口，保留的清单可用于重新安装。正在分析时需先完成或取消任务。

```json
{
  "api": 1,
  "id": "external.example-plotter",
  "executable": "example-plotter.exe",
  "title": {
    "en": "Example plotter",
    "zh-CN": "示例绘图"
  }
}
```

插件的 `title` 必须提供非空的英文名称。简体中文界面按 `zh-CN`、`zh-Hans`、`en` 的顺序选用首个非空名称。安装和扫描都会校验每个语言条目，名称须为字符串，整理空白后最多 80 个 UTF-16 代码单元。

可执行文件名必须与清单同目录。程序接收 `--input <SigMF 元数据绝对路径> --output <结果文件绝对路径> --language <en 或 zh-CN>`，成功时返回 0。运行目录和结果文件位于临时目录。清单可选的 `output` 字段默认是 `png`，原有清单仍可使用。选择 `text` 时，插件应写入非空 UTF-8 纯文本，大小不超过 1 MiB，工作区可以阅读、复制或导出为 TXT。PNG 文件最大 32 MiB，宽高各不得超过 4096 像素。

清单也可设置 `"output": "wav"`。插件应写入最多 32 MiB 的 16 位小端 PCM WAV，采用标准 44 字节头，单声道或双声道，采样率 8–192 kHz。工作区显示音频参数，可导出 WAV。包含 Qt Multimedia 的构建还可播放和停止，切换分析结果时会停止旧音频。

默认运行时限为 30 秒，研究工作区可取消任务。插件以当前用户权限运行，使用可信的可执行文件，插件需遵守输入只读约定。此接口用于录制研究，实时检测与其他输出类型将使用各自的接口。

支持区间分析的插件在清单中声明 `"sampleRange": true`。用户可在研究工作区选择 **样本** 或 **秒**，输入起点和样本数或时长，再选择 **分析区间**。起点从零算起。秒模式和 FM 中心频率均接受系统小数分隔符，也接受小数点。秒模式按录制采样率把起点和时长分别换算到最近的样本，半个样本向上取整。切换单位会清空输入，两项留空时沿用插件默认区间。只有声明支持区间的插件才会接收 `--first-sample N --samples N`，插件应按录制长度和自身资源上限校验参数。

工程提供原生 C++ 示例 **I/Q 功率报告**。构建后用 `cmake --install <构建目录> --config Release --component ResearchExamples --prefix <暂存目录>` 生成插件包，在管理器中选择 `research-plugins/power-report/power-report.json` 安装。它复用核心的 I/Q 功率统计，默认分析录制的前五秒，也可分析指定的最多五秒片段。报告包含全带平均功率、削波对数、归一化 I/Q 均值、样本格式和分析区间。输出语言与工作区一致。

桌面菜单栏提供 **检测** 和 **插件**。检测默认启用现有项目，可在开始会话前独立选择 LoRa、2-FSK／GFSK、OOK、ASK、广播 FM、BPSK、QPSK、4-FSK、OFDM 和 CSS。BPSK、QPSK 与 4-FSK 共用原生信道提取和突发定位。OFDM 验证重复的循环前缀并报告符号与前缀时长。CSS 用三种时频分辨率跟踪重复扫频，报告扫频方向、斜率、频率跨度、周期和次数。CSS 候选代表重复扫频证据，LoRa 结构另由专项检测器验证。原生片段识别可用于实时监听和桌面回放。原有实时窄带检测路径的开关仍作用于实时监听。

从菜单栏选择 **插件 → 管理插件…** 可集中管理内置插件。检测页与 **检测** 菜单共用勾选状态，会话运行时锁定。频谱、瀑布图和 I/Q 波形可以各自即时启停，检测和显示选项会保存到本机。更新前的频谱与瀑布组合选项用于初始化尚未保存的独立选项。研究插件页和 **插件 → 研究插件** 子菜单均可直接打开具体工具。工作区已经打开录制时，切换工具会分析同一份录制。正在分析时，工作区会在当前任务结束后切换到最后选择的工具。

片段检测的菜单选项、`scan --modulations` 和命令行帮助使用核心模块中的同一份检测器清单。清单定义稳定 ID、调制名称及对应开关。桌面偏好仍兼容旧版使用的 `detection/four-fsk` 键。核心按输入类型注册检测器。宽带检测器读取整段 I/Q，窄带分类器复用同一份信道提取和突发定位结果。窄带分类器按注册顺序尝试，首个匹配结果进入事件流，PSK 仍优先于 4-FSK。只有宽带检测器启用时，直接跳过窄带信道提取。

整个工程按 C++ 实现迁移。桌面运行时的调制识别和研究插件已完成迁移。LoRa 专项从录制数据重新确认结构，并显示去扫频 FFT、SFD、前导码功率谱和候选符号周期处的相关度。留空选区时，含事件索引的录制优先在索引附近搜索。手动指定区间时，结构检测和绘图均限定在该区间，图题注明原录制样本索引。手动区间最多 64 MiB，需包含足以确认结构的前导码和 SFD。现有 Python 遗留包括独立离线分析工具、诊断与部署脚本、回归驱动。应分批以 C++ 等效实现替换，逐项用相同输入验证后移除旧入口。

离线片段扫描已有原生入口，复用桌面的 CSS、OFDM、PSK 和 4-FSK 判据。

```sh
signalscope scan --input capture.sigmf-meta --modulations css,ofdm --first-sample 0
```

命令逐行输出 JSON，每行对应一个约四分之一秒的窗口，相邻窗口重叠一半。窗口和候选都使用录制内的绝对样本位置。同一个信号跨窗出现时，输出可能保留多条观测，便于对照各窗的证据。使用 `--first-sample` 和 `--samples` 限制分析区间。OFDM 检查采集窗口内的循环前缀，尚无中心频率估计。LoRa 结构和其余实时窄带判据仍通过各自入口分析。

### 解调产物的扩展契约

采集后端提供带绝对样本位置的 I/Q。监听和回放已共用 C++ I/Q 订阅接口，可在会话开始前注册多个处理模块。同一数据块在订阅回调期间以只读视图共享，附带采样格式、采样率、中心频率和连续性标记。回放采用录制元数据，实时订阅采用会话配置。一个订阅者异常时其余订阅者继续接收。监听保留采集线程的非阻塞订阅和低优先级分析线程的订阅两个入口，回放在自己的工作线程分发。各入口独立跟踪收到的样本位置，分析队列跳过数据时，只在分析入口的下一块标记断点。该标记反映软件交付的样本位置，硬件本身未报告的丢样仍无法据此判断。

在此基础上，解调插件可消费 I/Q 并产生一个或多个命名输出端口。协议解码、后续数学处理、文件导出和呈现插件通过这些端口连接。监听时可将接收机作为输入源，离线时使用录制作为输入源，处理节点复用同一套输入与输出契约。

每个端口公布稳定的格式 ID、版本和流描述。流描述携带该格式需要的参数，例如采样率、信道数、字节序、位序或协议模式。数据块携带流 ID、序号、对应原始 I/Q 的样本位置和连续性标记，以及由格式契约解释的数据。会话层依据格式 ID 和版本匹配端口，并据此提供可选的下一步操作。格式归提供它的模块管理，新增格式时可以独立提供解析器、转换器或呈现器。

- 广播 FM 解调器可以输出 PCM，音频插件声明可播放相应 PCM 格式。
- FSK 解调器可以输出软判决或比特流，帧同步器输出分帧结果，协议插件再从帧中提取结构化字段。
- 图像、视频、遥测和专有协议各有自己的格式契约。未知格式仍可导出字节、时序和来源信息，之后可用新插件重放和解析。

实时节点拥有有界队列和自己的处理线程。界面预览可以丢弃积压数据并报告断点，依赖连续性的解码节点应重置状态或明确报告数据不完整。离线回放可对输入施加背压。原始 I/Q 录制与可选处理链分开，保留原始样本索引用于定位派生产物。

当前已将 FM 的实时解调与 PCM 队列放到 FM 调制适配器，设备播放仍在桌面音频插件中。外部研究插件支持既有的 PNG、UTF-8 文本和 WAV 清单。新增产物可以在 `api: 1` 清单中声明 `"output": {"format": "vendor.telemetry-frames", "version": 1}`。格式 ID 使用带点分段的小写标识，版本为正整数。插件将至多 32 MiB 的原始字节写入 `--output` 指定的文件。研究面板展示格式 ID、版本和大小，默认导出文件名包含格式和版本。导出文件内容与插件生成的字节一致。旧版宿主只能读取字符串形式的输出声明。

离线产物可继续交给声明 `"api": 2` 和 `"input": {"format": "vendor.telemetry-frames", "version": 1}` 的处理插件。格式 ID 和版本都须匹配。研究面板在存在兼容插件时显示 **处理分析数据…**。宿主将产物的原始字节写入临时输入文件，以原有的 `--input`、`--output`、`--language` 参数启动插件。处理插件可输出报告、图像、WAV 或另一种二进制产物。取消或失败时保留上一步结果。实时流分发与多端口连接仍属于后续实现。

处理成功后，研究面板保留最近一次处理的输入产物。点击 **返回输入数据** 可恢复它的原始字节、格式、版本和导出名称，再选择其他兼容插件。开始一项新的录制分析时清空这一步历史。

## SDRplay RSPdx-R2 后端

SDRplay 官方 Hardware API 文档列出 RSPdx-R2 和 Windows、Linux、macOS 安装包。其 Linux 支持说明目前以 Ubuntu LTS 为验证范围。Debian 是本项目明确的实机验收目标，需检查驱动服务、USB 权限、ABI、采样与拔插恢复。uConsole RTL-SDR 路径保留为已验证基线。

实时采集通过独立的接收机接口使用 RTL-SDR。后端负责设备枚举、参数探测和连续样本流，监听与手动录制共用此接口。每个后端声明样本格式。采集队列、环形预录、事件切片和诊断录制支持 CU8 与 CI16，样本位置以复样本对为单位，容量上限以实际字节为单位。采集块不连续时停止并报告错误。RTL-SDR 继续使用 CU8。

离线链路支持原生 `ci16_le` SigMF。命令行可检查、裁剪、分析 LoRa，或用 `monitor --input` 验证自动事件录制。桌面可重放频谱、I/Q 波形和扩展调制分析，也能生成研究图。裁剪和事件文件保留原始位宽和字节。检测器直接从 16 位复样本转换为浮点。

SDRplay 后端通过 SoapySDR 0.8 和 SoapySDRPlay3 插件接收原生 CS16，保存为 `ci16_le`。构建时需提供 SoapySDR 开发包，运行时需提供与其 ABI 匹配的 SoapySDRPlay3 插件及厂商 Hardware API 服务。SDK 和运行时由各平台单独安装。缺少依赖时，录制回放和 RTL-SDR 仍可使用。

RSPdx‑R2 到货验收从 **2 MS/s、自动增益、天线 A 或 B** 开始。厂商 API 使用 **3.15 或更新版本**，SoapySDRPlay3 应能把设备识别为 `RSPdx-R2`。天线 C 是 200 MHz 以下使用的 BNC 口，AMC 会拒绝用它接收 478 MHz 或 821 MHz。桌面 SDRplay 调谐输入支持 1 kHz 至 2 GHz，接收机采样预设为 2、2.048 和 3 MS/s。2 MS/s 时程序选择并核对 1.536 MHz 中频滤波带宽，软件默认检测窗口为中心频率两侧各 500 kHz。 [SDRplay Hardware API](https://sdrplay.com/hardware-api/) · [RSPdx‑R2 规格](https://www.sdrplay.com/resources/RSPdxR2Datasheet.pdf) · [SoapySDRPlay3 驱动配置](https://github.com/pothosware/SoapySDRPlay3/blob/master/Settings.cpp)

接收机后端注册表提供稳定 ID、显示名称、默认增益和桌面增益预设。设备设置、会话来源和命令行帮助从同一份注册表读取。RTL-SDR 和 SDRplay 在设备设置中探测并应用后，桌面用当前设备报告的手动档位替换预设。SDRplay 显示的是中频增益衰减，候选档位来自驱动报告的 IFGR 范围和步长，并在启动采集时再次验证。如果原档位和后端默认档位均不可用，则使用自动增益。未探测时使用后端预设。自动增益的界面名称随语言切换，保存值仍为 `auto`。旧版 RTL-SDR 和 SDRplay 的设置键继续可用。

```sh
signalscope devices --receiver sdrplay
signalscope probe --receiver sdrplay --device 0
signalscope capture --receiver sdrplay --device 0 --frequency 470000000 --rate 2000000 --seconds 2 --output capture-rsp
signalscope-gui --receiver sdrplay --device 0
```

在接入实体设备后，先检查 `probe` 的 `hardware`、`hardware_info` 和天线列表。随后在目标频段保存两秒 I/Q，确认 `status` 为 `complete`、`accepted_pairs` 为 4,000,000，并核对实际频率、采样率、滤波带宽和天线。最后在桌面启动监听，验证调制结果、停止后重启和断开后的错误报告。实体测试应分别记录接收机、驱动、操作系统和采样参数。

2.048 MS/s 可用于录制及关闭 LoRa 的监听。现有 LoRa 检测器要求各候选带宽和扩频因子的每符号样本数符合整数与定时相位约束，默认 LoRa 配置可用 2 或 3 MS/s。桌面启动前按实际输入采样率校验，若不兼容则提示调整采样率或关闭 LoRa。

驱动报告溢出或突然中止时，采集报告使用 `reason_code: stream_discontinuity`，同时保留驱动返回值、标记和已接收样本数。模拟驱动在同一进程内验证了故障后释放旧流并重新打开设备。

SDRplay 的采集报告包含 `read_stats`，监听结束时可在 `source_result` 中查看，也可悬停在桌面状态行查看。它记录有效驱动读次数、低于本次请求长度的短读次数、超时次数、最小与最大读块样本数，以及合并后实际交付的块数。有效读统计包含稳定等待期间的样本，交付块数只统计交给下游的数据。

桌面可在停止监听后通过 **接收机设置** 选择后端、设备、天线口和采样率。第一批能力改造后，设备查询异步执行，采样率保留驱动报告的档位并根据有效范围提供常用选项，也可输入自定义整数。配置预检区分设备能力和监听分析限制。点击“应用”后实际配置并回读，成功后按后端保存选项。窗口新增频率、搜索宽度和增益联动反馈，完整契约见 [接收机能力与配置联动](13-接收机能力与配置联动.md)。命令行可用 `--antenna` 指定 `probe` 返回的 SDRplay 端口名，采集报告记录实际选择的端口。

`devices` 返回不可用时，`reason_code` 区分 `backend_not_built` 与 `driver_missing`，`reason` 保留诊断详情。桌面按原因显示本地化提示。后端可用而设备列表为空时，界面提示未找到接收机。

SDRplay 桌面设置会保存可唯一识别的设备序列号。设备枚举次序变化后，查询与采集仍选择同一台接收机。CLI 的 `probe`、`capture` 和 `monitor` 支持 `--serial SERIAL`，使用该参数时以序列号为准。序列号缺失或匹配多个条目时需要重新选择设备。

SDRplay 默认使用自动增益。命令行手动 `--gain` 表示整数 IF 增益衰减量，范围由 `probe` 返回。桌面在查询设备后显示驱动报告的可选手动衰减量。读取到溢出或驱动报告异常终止时，停止采集并保留错误报告。实体设备的采样率、增益、天线口、调谐边缘、连续性和恢复仍需分别验收。高采样率模式需先验证滤波和分信道，再扩大实时搜索带宽。

## 性能验收

同一台主机、同一输入、同一算法参数和同一显示范围，对照无界面、当前界面及候选界面。逐事件比较结构匹配、频率、BW/SF、录制覆盖与丢弃计数。连续采集记录分析与录制延迟、队列高水位、CPU、PSS 或平台等效指标、GPU 内存和帧时间。性能取舍以重复测量为准。若界面候选使既有检出率、连续采集或录制覆盖退化，则不进入发布。RTL-SDR 和 RSPdx-R2 分开验收。

Debian 13 ARM64 的 QEMU 验收中，LoRa 候选测试通过。窄带流水线以原速回放时扫描 3 个输入块、跳过 50 个，未识别预期的 FSK 事件，主分析路径的丢样计数为 0。同一测试设置 `AMC_TEST_MONITOR_REPLAY_SPEED=0.1` 后通过。慢速回放可验证 ARM64 的窄带检测和事件合并结果，实时吞吐仍须在目标设备上测量。

在 uConsole 的 Debian 13 ARM64 本机上，未设置慢速选项时，`live_fsk_pipeline` 回归通过。另以 1 倍速回放 100.8 MHz 广播 FM 的 1.75 MS/s 实录，主分析处理 700 万对 I/Q，丢样计数为 0，窄带路径扫描 214 个块、跳过 0 个，只产生一个广播 FM 事件。此结果覆盖本机原速回放；实体 RSPdx‑R2 的 USB 采集和持续吞吐单独验收。

在同一台 uConsole 上，模拟 SDRplay 模块以 2 MS/s、每次最多 4096 对 CS16 样本送入 15 秒。启用全部实时检测器时，扩大窄带队列前两次分别跳过 112 和 105 个块，扩大后分别跳过 5 和 6 个块。四次主分析与录制路径均处理了全部 3000 万对样本，主分析丢样为 0。模拟模块用 `AMC_TEST_SOAPY_REALTIME=1` 开启节拍，测试覆盖软件采集路径和短时积压。

监听时，状态行会标出窄带跳过的块数，悬停可查看窄带扫描数、跳过数和队列峰值。CLI 的 `fsk_analysis` 也记录 `queue_capacity_blocks` 与 `queue_high_water_blocks`。窄带跳块和主分析丢失的 I/Q 对数分开显示。

SDRplay 适配器在配置的采样块大小内合并连续短读，结束或故障时交付剩余的有效样本。默认 64 KiB 块包含 16,384 对 CS16。每次最多返回 4096 对样本的模拟驱动复测中，uConsole 在 2 MS/s 下处理 3000 万对样本，窄带扫描 1832 块、跳过 0 块，队列峰值为 2/8。

同一模拟驱动还在 475.125 MHz 生成约 7.5 毫秒的 2-FSK 突发。uConsole 以 2 MS/s 对比时，两版均处理全部 12 万对样本，主分析和窄带均无跳块。合并前未报告 FSK，合并后报告一个 FSK 候选，估计中心为 475.125 MHz。该用例加入了 SDRplay 回归，覆盖模拟驱动至实时监听的整条路径。

uConsole 中文桌面用离屏窗口启动 2 MS/s 的模拟 SDRplay 监听，保留默认检测选择。约 15 秒内录制路径消费全部 29,974,528 对样本，主分析队列丢弃计数为 0，窄带扫描 1830 块、跳过 0 块，检出 475.125 MHz 的 FSK 候选。应用退出时主分析留下最后 8192 对样本未处理，约为 4.1 毫秒。这项验证覆盖桌面启动和原速监听，实际窗口合成、实体 USB 和射频性能单独验收。

停止逻辑修正后，用相同配置复测桌面退出。采集、主分析和录制路径计数均为 27,656,192 对样本，主分析丢弃和窄带跳块均为 0，并再次检出模拟 FSK。停止采集后，主分析会继续处理已入队的有界数据，完成后才结束会话。会话运行时关闭窗口会请求后台收尾，完成后窗口自动关闭。

在 uConsole 上以模拟 SDRplay 驱动分别送样 30 秒。2.048 MS/s 关闭 LoRa 后，主分析和录制路径均处理 61,440,000 对样本，窄带跳过 0 块。3 MS/s 启用全部 CLI 实时检测器，独立复测时录制路径处理全部 90,000,000 对样本，主分析丢弃 20,709,376 对，窄带跳过 5476 块。uConsole 的全调制到货验收先用 2 MS/s。3 MS/s 的时序兼容性与实时吞吐须分别判断。

另以同一模拟源分别运行 15 秒。2 MS/s 全部 CLI 实时检测器和 3 MS/s 仅窄带检测均未丢样或跳块。3 MS/s 仅 LoRa 时主分析丢弃 7,382,336 对样本，全开时丢弃 7,316,800 对。全开并设四个 LoRa 工作者后仍丢弃 5,783,552 对，继续把采集块加到 128 KiB 时丢弃 6,071,616 对。各轮录制路径均消费了全部输入。这组对照将瓶颈定位到 uConsole 上的 LoRa 主分析路径，测试未覆盖实机 USB 传输或不同射频场景。
