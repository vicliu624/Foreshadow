# Engineering constraints

English · [简体中文](AGENTS.zh-CN.md)

This repository must comply with the [Extension Boundaries and Open/Closed Principle specification](docs/16-extension-boundaries.md). These are implementation and acceptance requirements. Splitting files or introducing interfaces alone is not evidence of compliance.

1. Before editing, identify the change axis, protocol owner, stable consumers, and assembly point. Device facts/rules belong to receiver plugins; detection semantics to detection modules; research tools/parameters to research providers; encoding rules to sample codecs.
2. Stable consumers must not import concrete vendor drivers or built-in research implementations, or add receiver/detector/research-tool ID branches. New implementations add providers, resources, and registration. Assembly belongs only at declared assembly points, not scattered through UI, sessions, or CLI.
3. Providers own parameter descriptions, dependencies, validation, recommendations, application, and readback. UI renders generic descriptions. Dependencies must evaluate the entire pending configuration.
4. Visible text uses resource keys. Do not maintain parallel multilingual tables in C++, concatenate translated sentences, or add language-specific branches. Plugin translations ship with the plugin. Add languages through resources and verify missing-key fallback.
5. I/Q parsing, byte counts, format names, normalization, and full-scale semantics come from codec interfaces. Algorithms, recording, and views must not assume that every non-CU8 input is CI16.
6. New events/detectors must display through descriptions and generic event fields. Unknown IDs must not cause information to disappear or be misclassified.
7. Preserve existing behavior and user data. Historical aliases are frozen migration protocols owned by the relevant module's metadata; they are not an extension route for new implementation branches.
8. When a new capability cannot be expressed by a protocol, explicitly upgrade the protocol and consumer capabilities. Do not pretend that adding a model alone supplies it. Do not turn every business condition into a plugin for abstraction's sake.
9. Run applicable architecture checks, contract tests, and existing regressions. Independently added providers/resources must demonstrate extension without stable-consumer edits. Tests that simply mirror implementation structure are insufficient.
10. Acceptance reports distinguish verified, unverified, and externally blocked platform behavior. Configuration compatibility does not guarantee detection, decoding, lossless real-time operation, or absence of hardware sample loss.
11. Distribution follows [Controlled Toolboxes and Online Updates](docs/17-toolboxes-and-updates.md). Catalog signing, generic installation transactions, package types, transport, and activation own their respective protocols. New toolboxes add only providers/resources/catalog entries; do not edit central UI or the generic installer. Daily CI uses self-hosted runners; hosted runners are for formal release builds. Release private keys stay outside the repository.
12. Desktop UI follows [Desktop Workspaces and Module Interfaces](docs/18-desktop-workspaces.md). Modulation-specific advanced parameters belong to the module, not the main window. Generic workspace management owns visibility/layout. View automatically registers panels; resizing must not reset user layout.
13. Real-time processing follows specification 16's resource boundaries. Budget queues by actual payload. Count acquisition, recording, and each analysis stage's losses separately. Status publication must not wait for another DSP pipeline. Performance changes require sustained-input evidence; short-recording success is not a long-term lossless guarantee.
14. Keep filesystem paths in their native type. Use `path_to_utf8` / `path_from_utf8` at JSON, Qt text, CLI, and other string boundaries; read native environment variables using `environment_utf8`. Do not depend on Windows code pages. Validate real release packages in paths containing Chinese and non-BMP characters, including the application, module discovery, and independent toolbox installation.

Documentation is maintained in English and Simplified Chinese, with English as the default. Update both language counterparts and `docs/documents.json`; run `python tools/docs/check_docs.py`. Preserve dated evidence and compatibility identifiers when updating current product descriptions. Foreshadow is the display brand; existing command names, settings roots, file formats, and package IDs remain compatibility protocols.
